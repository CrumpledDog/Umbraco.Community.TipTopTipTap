# E2E tests

A Playwright suite that exercises the package's one real behaviour end to end: pasting Word/Office-style
HTML into a Rich Text Editor with the **Office Paste Cleanup** extension enabled, and asserting (via a real
DOM parse, not substring matching) that the pasted debris is gone while genuinely meaningful markup
survives.

This is its own npm project (own `package.json`/`tsconfig.json`/`playwright.config.ts`), not part of
`src/Umbraco.Community.TipTopTipTap/Client` - it never ships in the package, it just drives a running
DemoSite through a real browser.

## Why a seed database instead of API-seeded fixtures

Rather than creating the Data Type/Document Type/content node via Management API calls in
`global-setup.ts` on every run, this suite restores a **committed SQLite database**
(`fixtures/seed.Umbraco.sqlite.db`) into place before the DemoSite starts, instead of letting it run a
fresh unattended install. This was a deliberate choice (over API-based seeding) because:

- The fixture content (a dedicated data type + document type + published content node) never changes
  between runs, so there's no need to pay the cost of creating it via API calls on every single test run,
  locally or in CI.
- It's easy to verify empirically that Umbraco boots straight into the seeded content instead of
  re-running unattended install (confirmed live - see "How the seed database boots" below) - there is no
  ambiguity about what state the site is in when tests start.

The trade-off is that the fixture must be regenerated by hand (see below) whenever the seed content needs
to change - e.g. if the property/document type schema needs to grow for a future test.

## Running locally

1. Restore the seed database into the DemoSite's data folder:
   ```bash
   cd tests/e2e
   npm ci
   npm run restore-seed-db
   ```
   This copies `fixtures/seed.Umbraco.sqlite.db` to
   `../../src/Umbraco.Community.TipTopTipTap.DemoSite/umbraco/Data/Umbraco.sqlite.db` (removing any stale
   `-wal`/`-shm` files first).

2. Build the Client bundle and start the DemoSite (needs to be reachable at `https://localhost:44399`):
   ```bash
   cd src/Umbraco.Community.TipTopTipTap/Client
   npm ci && npm run build
   cd ../../Umbraco.Community.TipTopTipTap.DemoSite
   dotnet run
   ```

3. In another terminal, run the tests:
   ```bash
   cd tests/e2e
   npx playwright install --with-deps chromium   # first time only
   npm test
   ```

The suite logs in as the seed database's unattended-install admin
(`dev@crumpled-dog.com` / `SuperSecret123!`, from
`src/Umbraco.Community.TipTopTipTap.DemoSite/appsettings.json`'s `Unattended` section - overridable via
`E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD`), reusing the authenticated session across tests via Playwright's
`storageState` (`global-setup.ts`).

Re-running `npm test` without restoring the seed DB again works fine - the test clears the Body Text
property's existing content (`Ctrl/Cmd+A`, `Delete`) before pasting, so repeated local runs stay
deterministic without needing a fresh database each time.

## How the seed database boots

Umbraco's unattended install only runs when there's no database (or an empty one) to migrate from -
restoring an already-migrated, already-installed SQLite file in its place makes Umbraco recognise the
install as already done and boot straight into the backoffice. This was confirmed live (not assumed):
after restoring the fixture into a completely clean `umbraco/Data` folder, the startup log shows normal
cold-boot cache-seeding messages (`Caching document URLs.`, `Cached 1 document URLs.`, etc.) with **no**
unattended-install or migration messages at all, and `/umbraco` returns `200` well within the CI health
check's retry budget.

## What's in the seed database

`fixtures/seed.Umbraco.sqlite.db` contains:

| Item | Name | Notes |
|---|---|---|
| Data Type | **Paste Test RTE** | Rich Text Editor (Tiptap). A dedicated data type, not the built-in "Richtext editor" - so this fixture is clearly test-owned and unaffected by any unrelated change to the built-in one. "Office Paste Cleanup" is enabled in its extensions (it defaults to enabled for any new Rich Text Editor data type; verified in the saved config rather than assumed). |
| Document Type | **Paste Test Page** (alias `pasteTestPage`) | One property, **Body Text** (alias `bodyText`), using the "Paste Test RTE" data type. Allowed at the content root. No template (not needed - the tests never render the front end). |
| Content node | **Paste Test** | Published, of type "Paste Test Page". Body Text starts empty; the test pastes into it. |

The built-in "Richtext editor" data type is untouched by this fixture.

## Regenerating the seed database

Needed if the seed content's schema has to change (e.g. adding a property for a future test). The
DemoSite's `Unattended` credentials (`appsettings.json`) must stay `dev@crumpled-dog.com` /
`SuperSecret123!` for `build-seed-db.mjs`'s defaults to work as-is (override via env vars otherwise).

1. Stop any running DemoSite, then wipe its database so a fresh unattended install runs:
   ```bash
   rm -rf src/Umbraco.Community.TipTopTipTap.DemoSite/umbraco/Data
   rm -rf src/Umbraco.Community.TipTopTipTap.DemoSite/umbraco/Logs
   ```

2. Build the Client bundle (needed for the backoffice UI to load) and start the DemoSite:
   ```bash
   cd src/Umbraco.Community.TipTopTipTap/Client
   npm ci && npm run build
   cd ../../Umbraco.Community.TipTopTipTap.DemoSite
   dotnet run
   ```
   Wait for it to finish the unattended install and start listening on `https://localhost:44399`.

3. In another terminal, run the seed-builder script. This drives the real backoffice via headless
   Chromium (Playwright) to create the data type, document type and content node described above:
   ```bash
   cd tests/e2e
   npm ci
   npx playwright install --with-deps chromium   # first time only
   node scripts/build-seed-db.mjs
   ```
   It prints a line for each step as it completes. Run it against a **freshly unattended-installed**
   DemoSite only - running it twice against the same database creates a second, oddly-suffixed
   "Paste Test RTE (1)" data type instead of reusing the first.

4. Stop the DemoSite, then copy the resulting database over the committed fixture:
   ```bash
   sqlite3 src/Umbraco.Community.TipTopTipTap.DemoSite/umbraco/Data/Umbraco.sqlite.db "PRAGMA wal_checkpoint(FULL);"
   cp src/Umbraco.Community.TipTopTipTap.DemoSite/umbraco/Data/Umbraco.sqlite.db tests/e2e/fixtures/seed.Umbraco.sqlite.db
   ```
   The `wal_checkpoint` first ensures any pending writes in the `-wal` file are flushed into the main
   database file before it's copied (the fixture is a single `.db` file - no `-wal`/`-shm` sidecars are
   committed).

5. Verify: wipe `umbraco/Data` again, run `npm run restore-seed-db` (from `tests/e2e`), start the DemoSite,
   and confirm it boots straight to a working backoffice with the "Paste Test" content node visible and
   published (see "How the seed database boots" above) - then run `npm test` and confirm it still passes.

6. Commit the updated `tests/e2e/fixtures/seed.Umbraco.sqlite.db`.

## CI

`.github/workflows/ci.yml` and `release.yml` both run this suite as their own `e2e` job, against the
**actual packed NuGet package** (same `dotnet remove reference`/`dotnet add package` swap the
`test-packages` job uses against a local flat NuGet folder source), not a `ProjectReference` build - so a
real packaging bug (a file missing from the package, a wrong static web asset path) would show up here too,
not just a build-time issue. The job restores `fixtures/seed.Umbraco.sqlite.db` into place before starting
the site, and uploads Playwright's own failure artifacts (trace/video/screenshot) plus the Umbraco startup
log on failure. `release.yml`'s `publish` job additionally requires `e2e` to pass before it will push
packages or cut a release.
